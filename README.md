## Блок 2. Таблица и модель данных

### Почему партиция организована по user_id?

События одного пользователя находятся в одной партиции. Его ленту можно
читать по `user_id`, не сканируя события других пользователей.

### Зачем нужен обратный порядок кластеризации по event_time?

Порядок `event_time DESC` размещает последние события первыми.
Запрос с `LIMIT` получает нужное число последних событий без дополнительной
сортировки в приложении.

## Блок 3. Вставка и чтение

### Сколько событий вставлено и сколько времени это заняло?

| Что вставлено | Сколько | Время |
|---|---|---|
| События пользователя 1001 (`login`, `purchase`, `view`) | 10 000 | 11,420 с |

Среднее время вставки одной записи в `user_actions`:
11,420 / 10 000 = 0,001142 с = 1,142 мс.

### Что даёт PreparedStatement?

Запрос подготавливается один раз перед циклом вставки и используется
повторно с новыми параметрами. Это сокращает затраты на повторный разбор
CQL сервером. Значения передаются отдельно через `bind`, без ручной
подстановки и экранирования в тексте запроса.
Переданные через `bind` значения воспринимаются как данные, а не как CQL-код,
что защищает от инъекций через эти параметры.

## Блок 4. Консистентность

### Каковы результаты замеров ONE и QUORUM?

| Уровень | Запись, мс | Чтение, мс |
|---|---|---|
| ONE | 1167 | 8 |
| QUORUM | 3280 | 6 |

Запись — суммарное время 1000 последовательных вставок. На QUORUM каждая
вставка ждёт подтверждения двух реплик вместо одной на ONE, поэтому
дополнительное ожидание накапливается. Это объясняет ожидаемое направление
разницы: в нашем прогоне QUORUM занял примерно в 2,8 раза больше времени.
Точная величина зависит и от нагрузки на стенд.

Чтение — один запрос 20 событий, поэтому оно намного быстрее 1000 вставок.
Данные могли оставаться в памяти, а небольшие задержки между локальными
узлами — сгладить разницу ONE и QUORUM. Разница 8 и 6 мс могла быть обычным
колебанием времени выполнения; одного замера недостаточно для вывода.

### Что означает формула W + R > N?

`W` — число реплик, подтверждающих запись, `R` — число реплик, участвующих
в чтении, `N` — replication factor, здесь 3. Если `W + R > N`, наборы
реплик записи и чтения обязательно пересекаются. Для QUORUM на обеих
операциях: `2 + 2 > 3`; для ONE: `1 + 1 > 3` неверно.

### Чем отличаются ONE и QUORUM и какие гарантии даёт QUORUM?

При записи ONE достаточно подтверждения одной реплики, QUORUM — двух из
трёх. Запись отправляется всем репликам независимо от выбранного уровня.
Чтение ONE допускает ответ одной реплики, которая может отставать;
QUORUM требует ответов двух реплик с согласованием версий.

После успешной записи QUORUM последующее чтение QUORUM увидит записанное
событие, если нет конкурирующего изменения этого ключа. Один QUORUM только
на чтении или только на записи при ONE на другой операции такой гарантии
не даёт: `2 + 1 = 3`. QUORUM допускает недоступность одной из трёх реплик,
но требует ожидания большего числа ответов, чем ONE.

### Какой уровень выбрать для ленты событий пользователя и почему?

Я бы выбрал QUORUM для записи и чтения: для ленты аудита важно видеть
подтверждённое действие сразу после записи. Цена — ожидание двух реплик
и невозможность выполнить операцию, когда доступна только одна.

## Блок 5. Сжатие

### Как отличаются размеры таблиц с LZ4 и без сжатия?

| Таблица | Space used (total), байт | SSTable count | SSTable Compression Ratio |
|---|---|---|---|
| `user_actions` (LZ4) | 34 916 | 1 | 0.40196 |
| `user_actions_none` (без сжатия) | 79 011 | 1 | -1.00000 |

После `flush` на узле `c1` таблица с LZ4 занимает на 55,8% меньше места.
Значение `-1` означает, что коэффициент сжатия не применяется.

### Каковы затраты сжатия при записи и чтении и почему оно выгодно здесь?

При записи SSTable во время flush и compaction сжатие расходует CPU;
при чтении сжатые блоки нужно распаковывать. Взамен уменьшаются размер
данных на диске и объём дискового ввода-вывода. Повторяющиеся типы событий
и структура JSON в `payload` хорошо сжимаются: в нашем замере экономия
места составила 55,8%.

## Блок 6. Bloom-фильтр

### Каковы значения метрик и что они означают?

| Показатель | Значение |
|---|---|
| Bloom filter false positives | 0 |
| Bloom filter false ratio | 0.00000 |

`False positives` — число случаев, когда фильтр допустил наличие ключа,
но в SSTable его не оказалось; `false ratio` — наблюдаемая доля ложных
срабатываний. Нулевые значения означают, что ложных срабатываний
не зарегистрировано, но не гарантируют их отсутствия при других запросах.

### Как Bloom-фильтр позволяет избежать поиска отсутствующего ключа на диске?

Фильтр хранится в памяти для каждой SSTable и проверяет ключ партиции
(`user_id`). Ответ «точно нет» позволяет пропустить поиск в этой SSTable
на диске. Ответ «возможно есть» требует дальнейшей проверки и может быть
ложноположительным. Поэтому отсутствие ключа не всегда исключает disk lookup.

### Когда Bloom-фильтр полезен, а когда его эффективность не важна?

Он полезен при точечных чтениях, когда нужного ключа нет во многих SSTable:
позволяет пропустить эти файлы. При редких чтениях или полном сканировании
данных его влияние невелико. Отсутствие отдельного события внутри существующей
партиции фильтр не определяет.

## Блок 7. Repair

### Что такое anti-entropy и зачем нужен nodetool repair?

Anti-entropy — сравнение и синхронизация данных реплик. `nodetool repair`
выявляет расхождения и передаёт недостающие данные между репликами вне пути
клиентского чтения, в том числе для редко читаемых данных.

### Когда repair необходим и что происходит без него?

Repair нужен после пропущенных обновлений, например при простое узла дольше
окна hinted handoff, и регулярно для устранения накопленных расхождений.
Без него чтение с отстающей реплики может вернуть устаревшие данные.
Удаления нужно распространить до истечения `gc_grace_seconds`, иначе после
удаления tombstones возможно возвращение старых данных. Сами tombstones
удаляет compaction; нерегулярный incremental repair также может задерживать
их очистку из-за разделения repaired и unrepaired SSTable.

### Чем repair отличается от read repair и hinted handoff?

`Read repair` исправляет обнаруженные при чтении расхождения только
в затронутых данных. `Hinted handoff` доставляет сохранённые координатором
обновления после краткого простоя реплики. `Nodetool repair` сравнивает
реплики в выбранных диапазонах независимо от клиентских чтений и наличия
хинтов, поэтому эти механизмы не заменяют его.

## Блок 8. Результаты и демонстрация

### Как воспроизвести результаты?

Из корня проекта при запущенном Docker:

```bash
docker compose up -d
docker compose run --rm lab reset
docker compose run --rm lab fixtures
docker compose run --rm lab all
bash ops.sh tablestats
bash ops.sh repair
docker compose run --rm lab metrics
```

`all` последовательно выполняет `data`, `bulk` и `consistency`.
После демонстрации стенд останавливается командой `docker compose down`.
